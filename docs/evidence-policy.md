# 証跡の区分ポリシー

**🌐 Language:** **日本語** | [English](en/evidence-policy.md)

---

## 結論

このリポジトリの記述のうち、**製品やサービスの挙動についての主張**には 4 段階の区分を付けます。読者（人と AI）は区分を見て、その記述をどこまで信頼して自分の環境に適用できるかを判断してください。

区分の語彙は [FSx for ONTAP Adoption Playbook](https://github.com/Yoshiki0705/FSx-for-ONTAP-Adoption-Playbook) と共通です。**2 つのリポジトリを行き来する読者が、同じ語を同じ意味で読めるようにするためです。**

| 区分 | 意味 | 必須の付随情報 |
|------|------|--------------|
| `verified` | 記載の環境で実際に再現した | 日付とリージョン（例: `verified 2026-07-19 / ap-northeast-1`） |
| `documented` | AWS / NetApp の公式ドキュメント、または実測を持つ別プロジェクトの記録に記載がある | 出典の URL または文書名 |
| `field-observation` | 一度観測したが再現確認をしていない | 「再現未確認」の明記 |
| `hypothesis` | 論理的に導いた推論で未検証 | 「未検証」の明記 |

---

## Playbook の区分との対応

同じ 4 語を使いますが、**このリポジトリは実装を扱うため、`verified` が指す対象が違います。**

| | Playbook | このリポジトリ |
|---|---|---|
| `verified` の対象 | ONTAP / FSx の挙動を検証環境で再現した | AWS API の応答形状、デプロイの成否、実装の動作を実環境またはコードで確認した |
| 主張の単位 | 1 ファイル = 1 論点（frontmatter で区分を持つ） | **1 ファイルに複数の主張が混在するため、主張ごとに行内ラベルを付ける** |
| 数値の扱い | 測定条件の全項目を併記 | 同じ。加えて「サンプル実行」と「本番見積もり」を必ず区別する |

**Playbook がこのリポジトリの実測を引用する場合、Playbook 側では `documented` になります。** `verified` は「そのリポジトリの著者がその環境で再現した」ことを主張する語なので、引用は満たしません。

---

## 書き方

行内ラベルを使います。主張の直前か直後に置きます。

```markdown
**[verified 2026-07-19 / ap-northeast-1]** AgentCore Gateway は ap-northeast-1 で利用でき、
Gateway → Lambda → S3 AP の呼び出しが動作した。

**[documented]** S3 Access Point 経由の要求は、設定した 1 つのファイルシステム ID で認可される。
出典: https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/...

**[field-observation]** S3 AP の Lifecycle が FAILED になった。AD DC の到達性が原因と考えているが、
**再現未確認**。

**[hypothesis]** `createConfigurationBundle` のパラメータ形状は SDK の型定義から推定した。**未検証**。
```

`scripts/check-evidence.py` が次を検査します。

- `verified` に日付（`YYYY-MM-DD`）とリージョンがあり、日付が未来でないこと
- `documented` に URL または文書名があること（同じ行か直後の 2 行以内）
- `field-observation` の近くに「再現未確認」があること
- `hypothesis` の近くに「未検証」があること
- 4 語以外の綴り（`VERIFIED` / `UNVERIFIED` などの旧表記）が残っていないこと

旧表記そのものを説明する行（この規約のような記述）には行末に `<!-- allow:legacy-marker -->` を付けます。**逃げ道を増やさないため、認めるのは行ごとの明示だけです。**

**旧表記の検査範囲は `AGENTS.md` と `docs/` `benchmarks/` 配下で、実行時に対象ファイル数を出力します。** 検出器は走査範囲でも沈黙するため、何を見たかを結果と併せて示します。`CHANGELOG.md` は各リリース時点の記録なので範囲外です（過去のエントリは当時の状態を表しています）。

## 区分が答えていないこと

**「公開資料に記載を見つけられなかった」は区分ではありません。** 製品の挙動についての主張ではなく、資料の状態についての主張です。とくに `hypothesis` を使わないでください。`hypothesis` は「推論がある」ことを意味するため、推論を持たないまま使うと、持っていない根拠を持っているように見えます。

本文に探索日と探索範囲を書いてください。「2026-07 時点で AWS の公式ドキュメントに記載を見つけられませんでした」のように、いつ・どこを探したかが分かる形にします。

**予算や時間が足りなかったことも区分を決めません。決めるのは出どころです。**

## 数値を書くときの条件

`verified` の数値には測定条件を併記します。条件のない数値は再現できず、再現できない数値は判断に使えません。

| 併記する項目 | 例 |
|---|---|
| 日付 | `2026-07-19` |
| リージョン | `ap-northeast-1` |
| 構成 | モデル ID、ベクトルストア、チャンキング戦略、フラグの組み合わせ |
| 測定方法 | ツール、並列度、ドキュメント数、実行回数 |

そのうえで次を区別します。混同すると、読者が誤った前提で設計します。

| 区別 | 混同したときに起きること |
|------|----------------------|
| サンプル実行 / 本番見積もり | 単発の測定値が容量計画やコスト見積もりの根拠になる |
| この検証環境 / 一般的なサービス上限 | 環境固有の値がサービスの仕様として引用される |
| 実装が存在する / デプロイされている | コードがあることを「動いている」と読まれる |
| AI の補助的な示唆 / 最終判断 | 自動判定の結果が人の確認なしに確定する |

**3 行目はこのリポジトリで実際に起きました。** `lambda/permissions/fsx-permission-service.ts` は ACL を読むコードを持ちますが、どの CDK スタックからもデプロイされていません。「実装済み」と書かれていたため、機構が動いていると読める状態でした。

## 本番に取り入れる前

区分は「どこまで信頼できるか」を示すだけで、あなたの環境で成り立つことを保証しません。

| 区分 | 本番前に行うこと |
|------|---------------|
| `verified` | 記載の環境との差分（リージョン、モデル ID、フラグの組み合わせ、ONTAP 版）を洗い出し、違えば再確認する |
| `documented` | 出典を開き、現行版でも同じ記述かを確認する |
| `field-observation` | 自環境で再現するかを確認する。再現しなければ前提として使えない |
| `hypothesis` | 検証してから使う。未検証の推論を設計の根拠にしない |

**不可逆な操作は検証環境での確認を省略できません。** データの削除、保持期間の設定、既存ボリュームへの変更が該当します。

---

## 区分の昇格・降格

| 遷移 | 必要な作業 |
|------|----------|
| → `verified` | 日付とリージョンを追加し、再現手順を本文に書く |
| → `documented` | 出典 URL を追加する。逐語引用は 30 語以内、原則は要約 |
| `verified` → `field-observation` | 再現しなくなった経緯を追記する。値は消さず履歴として残す |
| → `hypothesis` | 根拠が失われた理由を書く |

**降格は品質低下ではありません。** 証跡が失われたことを示すほうが、古い `verified` を残すより安全です。
