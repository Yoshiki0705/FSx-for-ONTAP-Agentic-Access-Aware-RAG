## 1. Smart-Routing-Verifizierung

### Testverfahren

1. Rufen Sie die CloudFront-URL auf und melden Sie sich als admin-Benutzer an
2. Aktivieren Sie **Smart Routing** in den Chat-Einstellungen
3. Senden Sie die folgenden 3 Arten von Abfragen und überprüfen Sie die Routing-Ergebnisse

### Testabfragen und erwartete Ergebnisse

| Abfrage | Erwartete Stufe | Erwartetes Modell | Prüfpunkt |
|--------|-----------|-----------|-------------|
| „Hallo" | Simple | Haiku 4.5 | Antwort-Metadaten enthalten `routingTier: simple` |
| „Bitte fassen Sie den Inhalt des Produktkatalogs zusammen" | Complex | Sonnet 3.5 v2 | Antwort-Metadaten enthalten `routingTier: complex` |
| „Analysieren Sie die Quartalsberichte aller Abteilungen abteilungsübergreifend und identifizieren Sie Möglichkeiten zur Kostensenkung" | Full-context | Opus 4 | Antwort-Metadaten enthalten `routingTier: full-context` |

### Überprüfung der CloudWatch-Metriken

```bash
# Routing-Verteilung überprüfen (letzte Stunde)
aws cloudwatch get-metric-statistics \
  --namespace SmartRouting \
  --metric-name RoutingCount \
  --dimensions Name=RoutingTier,Value=simple \
  --start-time $(date -u -v-1H +%Y-%m-%dT%H:%M:%S) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%S) \
  --period 300 \
  --statistics Sum \
  --region ap-northeast-1
```

### Erwartete CloudWatch-Logs-Ausgabe

```json
{
  "level": "INFO",
  "message": "Smart routing decision",
  "query": "Hallo",
  "classification": "simple",
  "confidence": 0.95,
  "selectedModel": "anthropic.claude-haiku-4-5-20251001-v1:0",
  "queryWordCount": 1,
  "hasAnalyticalTerms": false
}
```

## 2. Verifizierung von Transfer Family IAM Deny

### Testverfahren

Überprüfen Sie, dass Partnerbenutzer `.metadata.json`-Dateien nicht überschreiben können.

```bash
# 1. SFTP-Verbindung
sftp -i /path/to/partner-key \
  -o HostKeyAlgorithms=rsa-sha2-256,rsa-sha2-512 \
  partner-a@s-XXXXXXXXXXXXXXXXX.server.transfer.ap-northeast-1.amazonaws.com

# 2. Normaler Datei-Upload (sollte erfolgreich sein)
sftp> put test-document.pdf /uploads/partner-a/test-document.pdf

# 3. Versuch, .metadata.json zu überschreiben (sollte verweigert werden)
sftp> put fake-metadata.json /uploads/partner-a/test-document.pdf.metadata.json
```

### Erwartete Ergebnisse

```
# Normale Datei: Erfolg
Uploading test-document.pdf to /uploads/partner-a/test-document.pdf
test-document.pdf                                    100%  1234     12.3KB/s   00:00

# .metadata.json: Access Denied
Uploading fake-metadata.json to /uploads/partner-a/test-document.pdf.metadata.json
remote open("/uploads/partner-a/test-document.pdf.metadata.json"): Permission denied
```

### Überprüfung über CloudTrail

```bash
# Access-Denied-Ereignisse überprüfen
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=PutObject \
  --start-time $(date -u -v-1H +%Y-%m-%dT%H:%M:%S) \
  --region ap-northeast-1 \
  --query 'Events[?contains(CloudTrailEvent, `AccessDenied`)].{Time:EventTime,User:Username}'
```

### Screenshot-Erfassungspunkte

- [ ] SFTP-Terminal mit erfolgreichem normalem Datei-Upload
- [ ] SFTP-Terminal mit verweigertem `.metadata.json`-Upload
- [ ] Access-Denied-Ereignis in CloudTrail

## 3. Verifizierung von KB Auto-Sync

### Testverfahren

1. Fügen Sie dem S3 Access Point eine Testdatei hinzu
2. Überprüfen Sie, dass ein Scan innerhalb von 5 Minuten ausgeführt wird
3. Überprüfen Sie, dass ein Ingestion-Job startet und abgeschlossen wird

```bash
# 1. Testdatei zum S3 AP hinzufügen
aws s3api put-object \
  --bucket arn:aws:s3:ap-northeast-1:ACCOUNT:accesspoint/AP_NAME \
  --key test-auto-sync/new-document.md \
  --body ./test-document.md \
  --region ap-northeast-1

# 2. Zugehörige .metadata.json hinzufügen
aws s3api put-object \
  --bucket arn:aws:s3:ap-northeast-1:ACCOUNT:accesspoint/AP_NAME \
  --key test-auto-sync/new-document.md.metadata.json \
  --body ./test-metadata.json \
  --region ap-northeast-1

# 3. Lambda-Protokolle überwachen (Scan sollte innerhalb von 5 Minuten ausgeführt werden)
aws logs tail /aws/lambda/${PREFIX}-kb-auto-sync \
  --follow --region ap-northeast-1
```

### Erwartete Lambda-Protokollausgabe

```json
{
  "level": "INFO",
  "message": "Scan completed",
  "scanId": "scan-20260523-103000",
  "filesScanned": 15,
  "newFiles": 1,
  "changedFiles": 0,
  "unchangedFiles": 14,
  "triggerIngestion": true
}
```


## 4. Verifizierung von Capacity Guardrails

### Testverfahren

Führen Sie dieselbe Aktion in schneller Folge aus, um zu überprüfen, dass die Ratenbegrenzung ausgelöst wird.

```bash
# Guardrails-Lambda direkt aufrufen (zum Testen)
for i in 1 2 3 4; do
  echo "=== Attempt $i ==="
  aws lambda invoke \
    --function-name ${PREFIX}-capacity-monitor \
    --payload '{"action": "volume_resize", "volume_id": "vol-test", "new_size_gb": 100}' \
    --region ap-northeast-1 \
    /tmp/guardrail-response-$i.json
  cat /tmp/guardrail-response-$i.json
  echo ""
  sleep 2
done
```

### Erwartete Ergebnisse

```
=== Attempt 1 ===
{"decision": "ALLOWED", "reason": "All checks passed", "action_count": 1}

=== Attempt 2 ===
{"decision": "ALLOWED", "reason": "All checks passed", "action_count": 2}

=== Attempt 3 ===
{"decision": "ALLOWED", "reason": "All checks passed", "action_count": 3}

=== Attempt 4 ===
{"decision": "BLOCKED", "reason": "Rate limit exceeded: max 3 per hour for volume_resize", "action_count": 3}
```

### Überprüfung der CloudWatch-Metriken

```bash
# Guardrail-Entscheidungsmetriken
aws cloudwatch get-metric-statistics \
  --namespace FSxNOps/Guardrails \
  --metric-name GuardrailDecision \
  --dimensions Name=Action,Value=volume_resize Name=Decision,Value=BLOCKED \
  --start-time $(date -u -v-1H +%Y-%m-%dT%H:%M:%S) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%S) \
  --period 300 \
  --statistics Sum \
  --region ap-northeast-1
```

### Überprüfung des DynamoDB-Zustands

```bash
# Datensatz der Guardrail-Zustandstabelle überprüfen
aws dynamodb get-item \
  --table-name ${PREFIX}-guardrail-state \
  --key '{"action_name": {"S": "volume_resize"}}' \
  --region ap-northeast-1
```

### Erwarteter DynamoDB-Datensatz

```json
{
  "action_name": {"S": "volume_resize"},
  "action_count": {"N": "3"},
  "window_start": {"S": "2026-05-23T10:00:00Z"},
  "last_execution": {"S": "2026-05-23T10:05:00Z"},
  "ttl": {"N": "1716544800"}
}
```

### Screenshot-Erfassungspunkte

- [ ] Lambda-Ausführungsprotokolle (Übergang ALLOWED → BLOCKED)
- [ ] DynamoDB-Tabellendatensatz (mit TTL)
- [ ] CloudWatch-Metriken mit BLOCKED-Zählung

## 5. Verifizierung von Voice Chat WebRTC

### Voraussetzungen

- Bereitgestellt mit `enableVoiceChat=true`
- Pipecat Voice Agent auf AgentCore Runtime bereitgestellt (per CLI)
- KVS Signaling Channel erstellt

### Testverfahren

1. Rufen Sie die CloudFront-URL auf und melden Sie sich an
2. Klicken Sie auf das Mikrofonsymbol im Chat-Bildschirm
3. Überprüfen Sie den Ablauf: Spracheingabe → Textkonvertierung → RAG-Suche → Sprachausgabe

### Prüfpunkte

| Schritt | Zu überprüfen |
|---------|---------|
| WebRTC-Verbindung | Verbindung über KVS Signaling Channel hergestellt |
| Spracheingabe | Audio vom Mikrofon erfasst |
| STT | Audio in Text konvertiert |
| RAG-Suche | KB-Suche mit dem konvertierten Text ausgeführt |
| TTS | Suchergebnisse als Audio zurückgegeben |
| Fallback | Automatische Umschaltung auf die REST-API bei WebRTC-Fehler |

### Screenshot-Erfassungspunkte

- [ ] Voice-Chat-UI (während der Mikrofoneingabe)
- [ ] KVS-Signaling-Channel-Konsolenbildschirm
- [ ] Protokolle mit WebRTC → REST-Fallback
