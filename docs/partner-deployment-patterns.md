## 概要

本ドキュメントは、Permission-aware RAG システムをパートナー企業が複数顧客へ展開する際のアーキテクチャパターンを整理します。顧客ごとのデータ分離、認証分離、コスト分離の設計指針を提供します。

---

## 対象顧客・業種

| 業種 | ユースケース | 権限要件 |
|------|------------|---------|
| 製造 | 設計図面・技術文書の部門別検索 | 部門 × プロジェクト × 機密レベル |
| 金融 | 規制文書・内部レポートの権限付き検索 | 部署 × 役職 × 顧客情報分離 |
| 公共 | 政策文書・内部資料の部局別検索 | 部局 × 職位 × 公開/非公開 |
| 医療 | 手順書・研究資料の診療科別検索 | 診療科 × 職種 × 患者情報分離 |
| 法務 | 契約書・判例の案件別検索 | 案件 × 担当者 × クライアント分離 |
| 教育 | 教材・研究資料の学部別検索 | 学部 × 教職員/学生 × 研究室 |

## 展開パターン比較

### パターン A: 顧客ごとに AWS アカウント分離（推奨: エンタープライズ）

```
┌─────────────────────────────────────────────────────────┐
│ パートナー管理アカウント                                    │
│ ┌─────────────────┐  ┌─────────────────┐               │
│ │ CDK Pipelines   │  │ StackSets       │               │
│ │ / CodePipeline  │  │ (テンプレート配布)│               │
│ └────────┬────────┘  └────────┬────────┘               │
└──────────┼────────────────────┼─────────────────────────┘
           │                    │
    ┌──────┴──────┐      ┌─────┴──────┐      ┌──────────────┐
    │ 顧客A       │      │ 顧客B       │      │ 顧客C        │
    │ アカウント   │      │ アカウント   │      │ アカウント    │
    │             │      │             │      │              │
    │ ・FSx ONTAP │      │ ・FSx ONTAP │      │ ・FSx ONTAP  │
    │ ・Bedrock KB│      │ ・Bedrock KB│      │ ・Bedrock KB │
    │ ・Cognito   │      │ ・Cognito   │      │ ・Cognito    │
    │ ・DynamoDB  │      │ ・DynamoDB  │      │ ・DynamoDB   │
    │ ・CloudFront│      │ ・CloudFront│      │ ・CloudFront │
    └─────────────┘      └─────────────┘      └──────────────┘
```

**メリット**:
- 完全なデータ分離（AWS アカウント境界）
- 顧客ごとの請求分離
- セキュリティインシデントの影響範囲限定
- 顧客ごとの独立した運用・スケーリング

**デメリット**:
- アカウント管理の運用負荷
- 共通コンポーネントの重複コスト
- デプロイパイプラインの複雑化

**適用条件**:
- 顧客が独自の AWS アカウントを持つ場合
- 厳格なデータ分離要件がある場合（金融、医療、公共）
- 顧客数が 10 社以下の場合

```
│  │  │ (顧客A)  │  │ (顧客B)  │  │ (顧客C)  │               │    │
│  │  │          │  │          │  │          │               │    │
│  │  │ Vol-A1   │  │ Vol-B1   │  │ Vol-C1   │               │    │
│  │  │ Vol-A2   │  │ Vol-B2   │  │ Vol-C2   │               │    │

│  │ KB-A     │  │ KB-B     │  │ KB-C     │  ← テナントごとに KB  │
│  │ S3 AP-A  │  │ S3 AP-B  │  │ S3 AP-C  │  ← テナントごとに AP │
│  └──────────┘  └──────────┘  └──────────┘                      │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ 共有リソース                                               │    │
│  │ ・CloudFront + WAF（共有、パスベースルーティング）          │    │
│  │ ・Cognito User Pool（テナント属性で分離）                  │    │
│  │ ・DynamoDB（テナント ID パーティションキー）                │    │
│  └──────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────┘
```

**メリット**:
- 運用の集約（単一アカウント管理）
- 共通コンポーネントのコスト共有
- デプロイの簡素化

**デメリット**:
- データ分離がアプリケーションレベル（設定ミスのリスク）
- 請求の按分が必要
- ノイジーネイバー問題の可能性

**適用条件**:
- 顧客数が多い場合（10 社以上）
- コスト効率を重視する場合
- データ分離要件が比較的緩い場合

## テナント分離の設計要素

### 1. ストレージ分離

| 分離レベル | 方式 | データ分離強度 | コスト |
|-----------|------|-------------|--------|
| ファイルシステム分離 | 顧客ごとに FSx ファイルシステム | 最高 | 高 |
| SVM 分離 | 1 ファイルシステム内で SVM 分離 | 高 | 中 |
| ボリューム分離 | 1 SVM 内でボリューム分離 | 中 | 低 |
| プレフィックス分離 | 1 ボリューム内でディレクトリ分離 | 低 | 最低 |

**推奨**: SVM 分離（パターン B）または ファイルシステム分離（パターン A）

### 2. ベクトルストア分離

| 方式 | S3 Vectors | OpenSearch Serverless |
|------|-----------|---------------------|
| テナントごとに KB | KB + Index を分離 | KB + Collection を分離 |
| 共有 KB + メタデータフィルタ | `tenant_id` メタデータでフィルタ | `tenant_id` フィールドでフィルタ |

**推奨**: テナントごとに KB を分離（セキュリティ境界の明確化）

### 3. 認証分離

| 方式 | 説明 | 適用 |
|------|------|------|
| Cognito User Pool 分離 | テナントごとに User Pool | パターン A |
| Cognito グループ分離 | 共有 User Pool + テナントグループ | パターン B |
| カスタム属性分離 | `custom:tenant_id` 属性 | パターン B |
| 外部 IdP 分離 | テナントごとに OIDC/SAML IdP | パターン A/C |

### 4. ログ・監査分離

| リソース | 分離方式 |
|---------|---------|
| CloudWatch Logs | テナントごとにロググループ or プレフィックス |
| CloudTrail | テナントごとに Trail（パターン A）or 共有 Trail + フィルタ |
| DynamoDB 監査テーブル | `tenantId` パーティションキー |
| S3 ログバケット | テナントごとにプレフィックス + バケットポリシー |

### 5. KMS 暗号化分離

| 方式 | 説明 | コスト |
|------|------|--------|
| テナントごとに CMK | 完全な暗号化分離 | CMK × テナント数 |
| 共有 CMK + キーポリシー | コスト効率重視 | 1 CMK |
| テナント管理 CMK（BYOK） | 顧客が鍵を管理 | 顧客負担 |

## CDK による自動展開

### パートナーオンボーディング: Transfer Family SFTP インジェスション

パートナー企業が Web UI を使用できない場合（法務事務所、監査法人、規制当局など）、AWS Transfer Family SFTP サーバー経由でドキュメントを投入できます。`enableTransferFamily=true` で有効化すると、SFTP アップロード → FSx ONTAP S3 AP → 権限メタデータ自動生成 → Bedrock KB 自動同期のパイプラインが構築されます。

詳細は [README.md の Transfer Family セクション](../README.md) を参照してください。

### StackSets パターン（パターン A 向け）

```typescript
// パートナー管理アカウントから顧客アカウントへ展開
const stackSet = new CfnStackSet(this, 'TenantStackSet', {
  stackSetName: 'permission-aware-rag-tenant',
  templateBody: tenantTemplate,
  parameters: [
    { parameterKey: 'TenantId', parameterValue: tenantId },
    { parameterKey: 'TenantDomain', parameterValue: tenantDomain },
  ],
  permissionModel: 'SERVICE_MANAGED',
  autoDeployment: { enabled: true, retainStacksOnAccountRemoval: false },
});
```

### CDK Pipelines パターン（パターン C 向け）

```typescript
// テナントごとにステージを追加
for (const tenant of tenants) {
  pipeline.addStage(new TenantStage(this, `Tenant-${tenant.id}`, {
    env: { account: tenant.accountId, region: tenant.region },
    tenantConfig: tenant,
  }));
}
```

## 提案テンプレート

### Before / After

| 観点 | Before（現状） | After（本システム導入後） |
|------|--------------|------------------------|
| ファイル検索 | 共有フォルダを手動で探索、検索精度低い | AI が権限範囲内で最適な文書を提示 |
| 権限管理 | AI 利用時に権限境界が消失するリスク | 既存 NTFS ACL がそのまま AI に反映 |
| ナレッジ活用 | 部門間の知識分断、属人化 | 権限を守りつつ組織横断のナレッジ検索 |
| 運用負荷 | AI 用にデータコピー・権限再設定が必要 | FSx 上のデータをそのまま AI に接続 |

### PoC 成功条件

| 指標 | 目標値 | 計測方法 |
|------|--------|---------|
| 回答精度 | 80% 以上（人間評価） | 50 問の評価セットで判定 |
| 権限制御 | 違反 0 件 | 権限マトリクステストで検証 |
| 応答時間 | P95 < 10 秒 | CloudWatch メトリクス |
| 運用工数 | 既存比 50% 削減 | 管理者ヒアリング |

### 本番化時の追加検討事項

| カテゴリ | 検討事項 |
|---------|---------|
| ID 連携 | 既存 AD / IdP との SSO 連携、MFA 要件 |
| 監査 | 検索ログ保全、アクセス証跡、定期レビュー |
| データ分類 | 機密レベル定義、AI 利用可否の判定基準 |
| コスト管理 | 月額予算、スケーリング計画、コスト配分 |
| SLA | 可用性目標、RPO/RTO、サポート体制 |
| 法務 | 利用規約、データ処理契約、責任分界 |

## SFTP インジェスション提案シナリオ

### 顧客の課題

多くの企業は外部パートナー（法律事務所、監査法人、規制機関、取引先）とのドキュメント授受に課題を抱えています:

- パートナーは Web UI や AWS コンソールを使えない/使いたくない
- メール添付は容量制限・セキュリティリスクがある
- 受け取ったドキュメントを手動で KB に登録する運用負荷が高い
- パートナーが送ったドキュメントに不適切な権限が付与されるリスク

### 提案ストーリー

```
顧客: 「監査法人から毎月レポートが届くが、手動でシステムに取り込んでいる。
       自動化したいが、監査法人にAWSコンソールを使わせるわけにはいかない。」

提案: 「AWS Transfer Family で SFTP エンドポイントを提供します。
       監査法人は普段使っている SFTP クライアントでファイルを送るだけ。
       権限メタデータは管理者設定に基づいて自動生成されるので、
       監査法人が権限を操作することはできません。
       アップロードから5分以内にRAG検索可能になります。」
```

### 提案時のポイント

| ポイント | 説明 |
|---------|------|
| **パートナーの学習コスト** | ゼロ。既存の SFTP クライアント（FileZilla, WinSCP）をそのまま使用 |
| **セキュリティ** | IAM Deny で `.metadata.json` 上書き防止。権限はシステムが自動付与 |
| **運用負荷** | ゼロ。アップロード→メタデータ生成→KB取り込みが全自動 |
| **コスト** | Transfer Family: ~$0.30/プロトコル/時間 + $0.04/GB転送 |
| **導入期間** | CDK パラメータ1つ（`enableTransferFamily=true`）で有効化 |

### 適用業種と具体例

| 業種 | パートナー | ドキュメント例 | 権限設計 |
|------|-----------|-------------|---------|
| 金融 | 監査法人 | 監査レポート、内部統制評価 | 経理部 + 監査委員会のみ |
| 法務 | 法律事務所 | 契約書ドラフト、法的意見書 | 法務部 + 担当案件チームのみ |
| 製造 | サプライヤー | 品質検査報告書、納品書 | 品質管理部 + 調達部のみ |
| 医療 | 検査機関 | 検査結果レポート | 担当医 + 検査部のみ |
| 公共 | コンサルティング | 政策提言書、調査報告 | 担当部局のみ |

### デモシナリオ（5分）

1. SFTP でテストファイルをアップロード
2. 5分以内に `.metadata.json` が自動生成されることを確認
3. RAG チャットで「アップロードしたドキュメントの内容は？」と質問
4. 権限のあるユーザーにのみ回答されることを確認
5. 権限のないユーザーには回答されないことを確認
