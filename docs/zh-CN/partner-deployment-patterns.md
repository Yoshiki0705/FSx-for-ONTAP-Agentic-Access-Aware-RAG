## 概述

本文档整理了合作伙伴公司将 Permission-aware RAG 系统部署到多个客户时的架构模式。提供了按客户数据隔离、认证隔离和成本隔离的设计指南。

## 目标客户与行业

| 行业 | 使用场景 | 权限要求 |
|------|----------|----------|
| 制造业 | 按部门搜索设计图纸和技术文档 | 部门 × 项目 × 机密级别 |
| 金融 | 按权限搜索法规文档和内部报告 | 部门 × 角色 × 客户信息隔离 |

## 部署模式比较

### 模式 A：按客户 AWS 账户隔离（推荐：企业级）

```
┌─────────────────────────────────────────────────────────┐
│ 合作伙伴管理账户                                          │
│ ┌─────────────────┐  ┌─────────────────┐               │
│ │ CDK Pipelines   │  │ StackSets       │               │
│ │ / CodePipeline  │  │ (模板分发)       │               │
│ └────────┬────────┘  └────────┬────────┘               │
└──────────┼────────────────────┼─────────────────────────┘
           │                    │
    ┌──────┴──────┐      ┌─────┴──────┐      ┌──────────────┐
    │ 客户 A      │      │ 客户 B      │      │ 客户 C       │
    │ 账户        │      │ 账户        │      │ 账户         │
    │             │      │             │      │              │
    │ ・FSx ONTAP │      │ ・FSx ONTAP │      │ ・FSx ONTAP  │
    │ ・Bedrock KB│      │ ・Bedrock KB│      │ ・Bedrock KB │
    │ ・Cognito   │      │ ・Cognito   │      │ ・Cognito    │
    │ ・DynamoDB  │      │ ・DynamoDB  │      │ ・DynamoDB   │
    │ ・CloudFront│      │ ・CloudFront│      │ ・CloudFront │
    └─────────────┘      └─────────────┘      └──────────────┘
```

**优势**：
- 完全数据隔离（AWS 账户边界）
- 按客户计费分离
- 安全事件影响范围有限
- 每个客户独立运维和扩展

**劣势**：
- 账户管理运维开销
- 共享组件的重复成本
- 部署管道复杂性

**适用场景**：
- 客户拥有自己的 AWS 账户
- 存在严格的数据隔离要求（金融、医疗、公共部门）
- 客户数量在 10 个以内

### 模式 B：1 个账户内的 SVM / 卷 / 前缀隔离

```
┌─────────────────────────────────────────────────────────────────┐
│ 共享 AWS 账户                                                     │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ FSx for ONTAP 文件系统                                     │    │
│  │                                                            │    │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐               │    │
│  │  │ SVM-A    │  │ SVM-B    │  │ SVM-C    │               │    │
│  │  │(客户 A)  │  │(客户 B)  │  │(客户 C)  │               │    │
│  │  │ Vol-A1   │  │ Vol-B1   │  │ Vol-C1   │               │    │
│  │  │ Vol-A2   │  │ Vol-B2   │  │ Vol-C2   │               │    │
│  │  └──────────┘  └──────────┘  └──────────┘               │    │
│  └──────────────────────────────────────────────────────────┘    │
│                                                                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                      │
│  │ KB-A     │  │ KB-B     │  │ KB-C     │  ← 每租户一个 KB     │
│  │ S3 AP-A  │  │ S3 AP-B  │  │ S3 AP-C  │  ← 每租户一个 AP    │
│  └──────────┘  └──────────┘  └──────────┘                      │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ 共享资源                                                    │    │
│  │ ・CloudFront + WAF（共享，基于路径路由）                     │    │
│  │ ・Cognito User Pool（通过租户属性隔离）                     │    │
│  │ ・DynamoDB（租户 ID 分区键）                                │    │
│  └──────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────┘
```

**优势**：
- 统一运维（单账户管理）
- 共享组件的共同成本
- 简化部署

**劣势**：
- 应用层面的数据隔离（配置错误风险）
- 需要计费分摊
- 潜在的噪声邻居问题

**适用场景**：
- 客户数量较多（10+ 家公司）
- 优先考虑成本效率
- 数据隔离要求相对宽松

## 租户隔离设计要素

### 1. 存储隔离

| 隔离级别 | 方法 | 数据隔离强度 | 成本 |
|----------|------|-------------|------|
| 文件系统隔离 | 每客户一个 FSx 文件系统 | 最高 | 高 |
| SVM 隔离 | 1 个文件系统内的 SVM 隔离 | 高 | 中 |
| 卷隔离 | 1 个 SVM 内的卷隔离 | 中 | 低 |
| 前缀隔离 | 1 个卷内的目录隔离 | 低 | 最低 |

**推荐**：SVM 隔离（模式 B）或文件系统隔离（模式 A）

### 2. 向量存储隔离

| 方法 | S3 Vectors | OpenSearch Serverless |
|------|-----------|---------------------|
| 每租户一个 KB | 独立 KB + 索引 | 独立 KB + 集合 |
| 共享 KB + 元数据过滤 | 通过 `tenant_id` 元数据过滤 | 通过 `tenant_id` 字段过滤 |

**推荐**：每租户一个 KB（清晰的安全边界）

### 3. 认证隔离

| 方法 | 描述 | 适用模式 |
|------|------|----------|
| Cognito User Pool 隔离 | 每租户一个 User Pool | 模式 A |
| Cognito 组隔离 | 共享 User Pool + 租户组 | 模式 B |
| 自定义属性隔离 | `custom:tenant_id` 属性 | 模式 B |
| 外部 IdP 隔离 | 每租户一个 OIDC/SAML IdP | 模式 A/C |

### 4. 日志与审计隔离

| 资源 | 隔离方法 |
|------|----------|
| CloudWatch Logs | 每租户一个日志组或前缀 |
| CloudTrail | 每租户一个 Trail（模式 A）或共享 Trail + 过滤 |
| DynamoDB 审计表 | `tenantId` 分区键 |
| S3 日志桶 | 每租户一个前缀 + 桶策略 |

### 5. KMS 加密隔离

| 方法 | 描述 | 成本 |
|------|------|------|
| 每租户一个 CMK | 完全加密隔离 | CMK × 租户数 |
| 共享 CMK + 密钥策略 | 成本效率优先 | 1 个 CMK |
| 租户管理的 CMK（BYOK） | 客户管理密钥 | 客户承担成本 |

## 使用 CDK 自动化部署

### StackSets 模式（用于模式 A）

```typescript
// 从合作伙伴管理账户部署到客户账户
const stackSet = new CfnStackSet(this, 'TenantStackSet', {
  stackSetName: 'permission-aware-rag-tenant',
  templateBody: tenantTemplate,
  parameters: [
    { parameterKey: 'TenantId', parameterValue: tenantId },
    { parameterKey: 'TenantDomain', parameterValue: tenantDomain },
  ],
  permissionModel: 'SERVICE_MANAGED',
  autoDeployment: { enabled: true, retainStacksOnAccountRemoval: false },
});
```

### CDK Pipelines 模式（用于模式 C）

```typescript
// 为每个租户添加一个阶段
for (const tenant of tenants) {
  pipeline.addStage(new TenantStage(this, `Tenant-${tenant.id}`, {
    env: { account: tenant.accountId, region: tenant.region },
    tenantConfig: tenant,
  }));
}
```

## 提案模板

### 前后对比

| 方面 | 之前（当前状态） | 之后（使用本系统） |
|------|-----------------|-------------------|
| 文件搜索 | 手动浏览共享文件夹，搜索精度低 | AI 在权限范围内呈现最优文档 |
| 权限管理 | AI 使用时权限边界消失的风险 | 现有 NTFS ACL 直接反映到 AI |
| 知识利用 | 部门间知识孤岛，依赖个人 | 尊重权限的跨组织知识搜索 |
| 运维开销 | AI 需要数据复制和权限重新配置 | 将 FSx 上的数据直接连接到 AI |

### PoC 成功标准

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 回答准确率 | 80%+（人工评估） | 使用 50 题评估集判定 |
| 权限控制 | 0 次违规 | 通过权限矩阵测试验证 |
| 响应时间 | P95 < 10 秒 | CloudWatch 指标 |
| 运维工作量 | 比当前减少 50% | 管理员访谈 |

### 生产化的额外考虑事项

| 类别 | 考虑事项 |
|------|----------|
| ID 联合 | 与现有 AD / IdP 的 SSO 集成、MFA 要求 |
| 审计 | 搜索日志保留、访问追踪、定期审查 |
| 数据分类 | 机密级别定义、AI 使用资格标准 |
| 成本管理 | 月度预算、扩展计划、成本分摊 |
| SLA | 可用性目标、RPO/RTO、支持体制 |
| 法律 | 服务条款、数据处理协议、责任边界 |
