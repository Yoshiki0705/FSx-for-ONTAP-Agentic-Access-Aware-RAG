**🌐 Language:** [日本語](../partner-deployment-patterns.md) | [English](../en/partner-deployment-patterns.md) | **한국어** | [简体中文](../zh-CN/partner-deployment-patterns.md) | [繁體中文](../zh-TW/partner-deployment-patterns.md) | [Français](../fr/partner-deployment-patterns.md) | [Deutsch](../de/partner-deployment-patterns.md) | [Español](../es/partner-deployment-patterns.md)

**상태**: 초안

## 개요

이 문서는 파트너 기업이 Permission-aware RAG 시스템을 여러 고객에게 배포할 때의 아키텍처 패턴을 정리합니다. 고객별 데이터 격리, 인증 격리, 비용 격리를 위한 설계 가이드라인을 제공합니다.

---

## 대상 고객 & 산업

| 산업 | 사용 사례 | 권한 요구사항 |
|------|----------|--------------|
| 제조업 | 설계 도면 및 기술 문서의 부서별 검색 | 부서 × 프로젝트 × 기밀 수준 |
| 금융 | 규정 문서 및 내부 보고서의 권한 기반 검색 | 부서 × 역할 × 고객 정보 격리 |
| 공공 부문 | 정책 문서 및 내부 자료의 부서별 검색 | 부서 × 직위 × 공개/비공개 |
| 의료 | 절차 매뉴얼 및 연구 자료의 부서별 검색 | 부서 × 직종 × 환자 정보 격리 |
| 법률 | 계약서 및 판례의 사건별 검색 | 사건 × 담당자 × 고객 격리 |
| 교육 | 교재 및 연구 자원의 학부별 검색 | 학부 × 교직원/학생 × 연구실 |

## 배포 패턴 비교

### 패턴 A: 고객별 AWS 계정 격리 (권장: 엔터프라이즈)

```
┌─────────────────────────────────────────────────────────┐
│ 파트너 관리 계정                                          │
│ ┌─────────────────┐  ┌─────────────────┐               │
│ │ CDK Pipelines   │  │ StackSets       │               │
│ │ / CodePipeline  │  │ (템플릿 배포)    │               │
│ └────────┬────────┘  └────────┬────────┘               │
└──────────┼────────────────────┼─────────────────────────┘
           │                    │
    ┌──────┴──────┐      ┌─────┴──────┐      ┌──────────────┐
    │ 고객 A      │      │ 고객 B      │      │ 고객 C       │
    │ 계정        │      │ 계정        │      │ 계정         │
    │             │      │             │      │              │
    │ ・FSx ONTAP │      │ ・FSx ONTAP │      │ ・FSx ONTAP  │
    │ ・Bedrock KB│      │ ・Bedrock KB│      │ ・Bedrock KB │
    │ ・Cognito   │      │ ・Cognito   │      │ ・Cognito    │
    │ ・DynamoDB  │      │ ・DynamoDB  │      │ ・DynamoDB   │
    │ ・CloudFront│      │ ・CloudFront│      │ ・CloudFront │
    └─────────────┘      └─────────────┘      └──────────────┘
```

**장점**:
- 완전한 데이터 격리 (AWS 계정 경계)
- 고객별 청구 분리
- 보안 인시던트의 제한된 영향 범위
- 고객별 독립적인 운영 및 스케일링

**단점**:
- 계정 관리 운영 오버헤드
- 공유 컴포넌트의 중복 비용
- 배포 파이프라인 복잡성

**적용 시기**:
- 고객이 자체 AWS 계정을 보유
- 엄격한 데이터 격리 요구사항 존재 (금융, 의료, 공공 부문)
- 고객 수가 10개 이하

### 패턴 B: 1 계정 내 SVM / 볼륨 / 접두사 격리

```
┌─────────────────────────────────────────────────────────────────┐
│ 공유 AWS 계정                                                     │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ FSx for ONTAP 파일 시스템                                   │    │
│  │                                                            │    │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐               │    │
│  │  │ SVM-A    │  │ SVM-B    │  │ SVM-C    │               │    │
│  │  │(고객 A)  │  │(고객 B)  │  │(고객 C)  │               │    │
│  │  │ Vol-A1   │  │ Vol-B1   │  │ Vol-C1   │               │    │
│  │  │ Vol-A2   │  │ Vol-B2   │  │ Vol-C2   │               │    │
│  │  └──────────┘  └──────────┘  └──────────┘               │    │
│  └──────────────────────────────────────────────────────────┘    │
│                                                                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                      │
│  │ KB-A     │  │ KB-B     │  │ KB-C     │  ← 테넌트별 KB       │
│  │ S3 AP-A  │  │ S3 AP-B  │  │ S3 AP-C  │  ← 테넌트별 AP      │
│  └──────────┘  └──────────┘  └──────────┘                      │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ 공유 리소스                                                 │    │
│  │ ・CloudFront + WAF (공유, 경로 기반 라우팅)                │    │
│  │ ・Cognito User Pool (테넌트 속성으로 격리)                 │    │
│  │ ・DynamoDB (테넌트 ID 파티션 키)                           │    │
│  └──────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────┘
```

**장점**:
- 통합 운영 (단일 계정 관리)
- 공통 컴포넌트의 공유 비용
- 간소화된 배포

**단점**:
- 애플리케이션 레벨의 데이터 격리 (구성 오류 위험)
- 청구 배분 필요
- 잠재적 노이지 네이버 문제

**적용 시기**:
- 고객 수가 많음 (10개 이상)
- 비용 효율성 우선
- 데이터 격리 요구사항이 비교적 완화

## 테넌트 격리 설계 요소

### 1. 스토리지 격리

| 격리 수준 | 방법 | 데이터 격리 강도 | 비용 |
|-----------|------|-----------------|------|
| 파일 시스템 격리 | 고객별 FSx 파일 시스템 | 최고 | 높음 |
| SVM 격리 | 1 파일 시스템 내 SVM 격리 | 높음 | 중간 |
| 볼륨 격리 | 1 SVM 내 볼륨 격리 | 중간 | 낮음 |
| 접두사 격리 | 1 볼륨 내 디렉토리 격리 | 낮음 | 최저 |

**권장**: SVM 격리 (패턴 B) 또는 파일 시스템 격리 (패턴 A)

### 2. 벡터 스토어 격리

| 방법 | S3 Vectors | OpenSearch Serverless |
|------|-----------|---------------------|
| 테넌트별 KB | 별도 KB + 인덱스 | 별도 KB + 컬렉션 |
| 공유 KB + 메타데이터 필터 | `tenant_id` 메타데이터로 필터 | `tenant_id` 필드로 필터 |

**권장**: 테넌트별 KB (명확한 보안 경계)

### 3. 인증 격리

| 방법 | 설명 | 적용 패턴 |
|------|------|-----------|
| Cognito User Pool 격리 | 테넌트별 User Pool | 패턴 A |
| Cognito 그룹 격리 | 공유 User Pool + 테넌트 그룹 | 패턴 B |
| 커스텀 속성 격리 | `custom:tenant_id` 속성 | 패턴 B |
| 외부 IdP 격리 | 테넌트별 OIDC/SAML IdP | 패턴 A/C |

### 4. 로그 & 감사 격리

| 리소스 | 격리 방법 |
|--------|-----------|
| CloudWatch Logs | 테넌트별 로그 그룹 또는 접두사 |
| CloudTrail | 테넌트별 Trail (패턴 A) 또는 공유 Trail + 필터 |
| DynamoDB 감사 테이블 | `tenantId` 파티션 키 |
| S3 로그 버킷 | 테넌트별 접두사 + 버킷 정책 |

### 5. KMS 암호화 격리

| 방법 | 설명 | 비용 |
|------|------|------|
| 테넌트별 CMK | 완전한 암호화 격리 | CMK × 테넌트 수 |
| 공유 CMK + 키 정책 | 비용 효율성 우선 | 1 CMK |
| 테넌트 관리 CMK (BYOK) | 고객이 키 관리 | 고객 부담 |

## CDK를 활용한 자동 배포

### StackSets 패턴 (패턴 A용)

```typescript
// 파트너 관리 계정에서 고객 계정으로 배포
const stackSet = new CfnStackSet(this, 'TenantStackSet', {
  stackSetName: 'permission-aware-rag-tenant',
  templateBody: tenantTemplate,
  parameters: [
    { parameterKey: 'TenantId', parameterValue: tenantId },
    { parameterKey: 'TenantDomain', parameterValue: tenantDomain },
  ],
  permissionModel: 'SERVICE_MANAGED',
  autoDeployment: { enabled: true, retainStacksOnAccountRemoval: false },
});
```

### CDK Pipelines 패턴 (패턴 C용)

```typescript
// 각 테넌트에 대한 스테이지 추가
for (const tenant of tenants) {
  pipeline.addStage(new TenantStage(this, `Tenant-${tenant.id}`, {
    env: { account: tenant.accountId, region: tenant.region },
    tenantConfig: tenant,
  }));
}
```

## 제안 템플릿

### Before / After

| 측면 | Before (현재 상태) | After (본 시스템 도입 후) |
|------|-------------------|--------------------------|
| 파일 검색 | 공유 폴더 수동 탐색, 낮은 검색 정확도 | AI가 권한 범위 내 최적 문서 제시 |
| 권한 관리 | AI 사용 시 권한 경계 소실 위험 | 기존 NTFS ACL이 AI에 직접 반영 |
| 지식 활용 | 부서 간 지식 사일로, 개인 의존 | 권한을 존중하면서 조직 횡단 지식 검색 |
| 운영 부담 | AI용 데이터 복사 및 권한 재구성 필요 | FSx의 데이터를 직접 AI에 연결 |

### PoC 성공 기준

| 지표 | 목표 값 | 측정 방법 |
|------|---------|-----------|
| 답변 정확도 | 80%+ (인간 평가) | 50문항 평가 세트로 판정 |
| 권한 제어 | 0건 위반 | 권한 매트릭스 테스트로 검증 |
| 응답 시간 | P95 < 10초 | CloudWatch 지표 |
| 운영 노력 | 현재 대비 50% 감소 | 관리자 인터뷰 |

### 프로덕션 추가 고려사항

| 카테고리 | 고려사항 |
