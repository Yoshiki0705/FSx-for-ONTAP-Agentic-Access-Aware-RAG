## 1. Vérification de Smart Routing

### Procédure de test

1. Accédez à l'URL CloudFront et connectez-vous en tant qu'utilisateur admin
2. Activez **Smart Routing** dans les paramètres de chat
3. Envoyez les 3 types de requêtes suivants et vérifiez les résultats de routage

### Requêtes de test et résultats attendus

| Requête | Niveau attendu | Modèle attendu | Point de vérification |
|--------|-----------|-----------|-------------|
| « Bonjour » | Simple | Haiku 4.5 | Les métadonnées de réponse contiennent `routingTier: simple` |
| « Veuillez résumer le contenu du catalogue de produits » | Complex | Sonnet 3.5 v2 | Les métadonnées de réponse contiennent `routingTier: complex` |
| « Analysez de manière transversale les rapports trimestriels de tous les services et identifiez les opportunités de réduction des coûts » | Full-context | Opus 4 | Les métadonnées de réponse contiennent `routingTier: full-context` |

### Vérification des métriques CloudWatch

```bash
# Vérifier la distribution du routage (dernière heure)
aws cloudwatch get-metric-statistics \
  --namespace SmartRouting \
  --metric-name RoutingCount \
  --dimensions Name=RoutingTier,Value=simple \
  --start-time $(date -u -v-1H +%Y-%m-%dT%H:%M:%S) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%S) \
  --period 300 \
  --statistics Sum \
  --region ap-northeast-1
```

### Sortie CloudWatch Logs attendue

```json
{
  "level": "INFO",
  "message": "Smart routing decision",
  "query": "Bonjour",
  "classification": "simple",
  "confidence": 0.95,
  "selectedModel": "anthropic.claude-haiku-4-5-20251001-v1:0",
  "queryWordCount": 1,
  "hasAnalyticalTerms": false
}
```

- [ ] Interface de chat affichant le niveau de routage

## 2. Vérification de Transfer Family IAM Deny

### Procédure de test

Vérifiez que les utilisateurs partenaires ne peuvent pas écraser les fichiers `.metadata.json`.

```bash
# 1. Connexion SFTP
sftp -i /path/to/partner-key \
  -o HostKeyAlgorithms=rsa-sha2-256,rsa-sha2-512 \
  partner-a@s-XXXXXXXXXXXXXXXXX.server.transfer.ap-northeast-1.amazonaws.com

# 2. Téléversement d'un fichier normal (devrait réussir)
sftp> put test-document.pdf /uploads/partner-a/test-document.pdf

# 3. Tentative d'écrasement de .metadata.json (devrait être refusée)
sftp> put fake-metadata.json /uploads/partner-a/test-document.pdf.metadata.json
```

### Résultats attendus

```
# Fichier normal : Succès
Uploading test-document.pdf to /uploads/partner-a/test-document.pdf
test-document.pdf                                    100%  1234     12.3KB/s   00:00

# .metadata.json: Access Denied
Uploading fake-metadata.json to /uploads/partner-a/test-document.pdf.metadata.json
remote open("/uploads/partner-a/test-document.pdf.metadata.json"): Permission denied
```

### Vérification via CloudTrail

```bash
# Vérifier les événements Access Denied
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=PutObject \
  --start-time $(date -u -v-1H +%Y-%m-%dT%H:%M:%S) \
  --region ap-northeast-1 \
  --query 'Events[?contains(CloudTrailEvent, `AccessDenied`)].{Time:EventTime,User:Username}'
```

### Points de capture d'écran

- [ ] Terminal SFTP montrant un téléversement de fichier normal réussi
- [ ] Terminal SFTP montrant le téléversement de `.metadata.json` refusé
- [ ] Événement Access Denied dans CloudTrail

## 3. Vérification de KB Auto-Sync

### Procédure de test

1. Ajoutez un fichier de test au S3 Access Point
2. Vérifiez qu'une analyse s'exécute dans les 5 minutes
3. Vérifiez qu'une tâche d'ingestion démarre et se termine

```bash
# 1. Ajouter un fichier de test au S3 AP
aws s3api put-object \
  --bucket arn:aws:s3:ap-northeast-1:ACCOUNT:accesspoint/AP_NAME \
  --key test-auto-sync/new-document.md \
  --body ./test-document.md \
  --region ap-northeast-1

# 2. Ajouter le .metadata.json correspondant
aws s3api put-object \
  --bucket arn:aws:s3:ap-northeast-1:ACCOUNT:accesspoint/AP_NAME \
  --key test-auto-sync/new-document.md.metadata.json \
  --body ./test-metadata.json \
  --region ap-northeast-1

# 3. Surveiller les journaux Lambda (l'analyse devrait s'exécuter dans les 5 minutes)
aws logs tail /aws/lambda/${PREFIX}-kb-auto-sync \
  --follow --region ap-northeast-1
```

### Sortie de journal Lambda attendue

```json
{

  "message": "Scan completed",

  "filesScanned": 15,
```


## 4. Vérification de Capacity Guardrails

### Procédure de test

Exécutez la même action en succession rapide pour vérifier que la limitation de débit est déclenchée.

```bash
# Invoquer directement la Lambda Guardrails (pour les tests)
for i in 1 2 3 4; do
  echo "=== Attempt $i ==="
  aws lambda invoke \
    --function-name ${PREFIX}-capacity-monitor \
    --payload '{"action": "volume_resize", "volume_id": "vol-test", "new_size_gb": 100}' \
    --region ap-northeast-1 \
    /tmp/guardrail-response-$i.json
  cat /tmp/guardrail-response-$i.json
  echo ""
  sleep 2
done
```

### Résultats attendus

```
=== Attempt 1 ===
{"decision": "ALLOWED", "reason": "All checks passed", "action_count": 1}

=== Attempt 2 ===
{"decision": "ALLOWED", "reason": "All checks passed", "action_count": 2}

=== Attempt 3 ===
{"decision": "ALLOWED", "reason": "All checks passed", "action_count": 3}

=== Attempt 4 ===
{"decision": "BLOCKED", "reason": "Rate limit exceeded: max 3 per hour for volume_resize", "action_count": 3}
```

### Vérification des métriques CloudWatch

```bash
# Métriques de décision du garde-fou
aws cloudwatch get-metric-statistics \
  --namespace FSxNOps/Guardrails \
  --metric-name GuardrailDecision \
  --dimensions Name=Action,Value=volume_resize Name=Decision,Value=BLOCKED \
  --start-time $(date -u -v-1H +%Y-%m-%dT%H:%M:%S) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%S) \
  --period 300 \
  --statistics Sum \
  --region ap-northeast-1
```

### Vérification de l'état DynamoDB

```bash
# Vérifier l'enregistrement de la table d'état du garde-fou
aws dynamodb get-item \
  --table-name ${PREFIX}-guardrail-state \
  --key '{"action_name": {"S": "volume_resize"}}' \
  --region ap-northeast-1
```

### Enregistrement DynamoDB attendu

```json
{
  "action_name": {"S": "volume_resize"},
  "action_count": {"N": "3"},
  "window_start": {"S": "2026-05-23T10:00:00Z"},
  "last_execution": {"S": "2026-05-23T10:05:00Z"},
  "ttl": {"N": "1716544800"}
}
```

### Points de capture d'écran

- [ ] Journaux d'exécution Lambda (transition ALLOWED → BLOCKED)
- [ ] Enregistrement de la table DynamoDB (avec TTL)
- [ ] Métriques CloudWatch montrant le compteur BLOCKED

## 5. Vérification de Voice Chat WebRTC

### Prérequis

- Déployé avec `enableVoiceChat=true`
- Pipecat Voice Agent déployé sur AgentCore Runtime (via CLI)
- KVS Signaling Channel créé

### Procédure de test

1. Accédez à l'URL CloudFront et connectez-vous
2. Cliquez sur l'icône du microphone sur l'écran de chat
3. Vérifiez le flux : entrée vocale → conversion en texte → recherche RAG → sortie vocale

### Points de vérification

| Étape | Élément à vérifier |
|---------|---------|
| Connexion WebRTC | Connexion établie via KVS Signaling Channel |
| Entrée vocale | Audio capturé depuis le microphone |
| STT | Audio converti en texte |
| Recherche RAG | Recherche KB exécutée avec le texte converti |
| TTS | Résultats de recherche renvoyés en audio |
| Repli | Bascule automatique vers l'API REST en cas d'échec de WebRTC |

### Points de capture d'écran

- [ ] Interface Voice Chat (pendant l'entrée microphone)
- [ ] Écran de la console KVS Signaling Channel
- [ ] Journaux montrant le repli WebRTC → REST
